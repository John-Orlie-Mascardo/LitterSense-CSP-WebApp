# RFID preference navigation — task 2

## Scope and cause

The user reported that the RFID Entry/Exit preference briefly switches Off and On whenever Settings is reopened, despite having enabled it.

Each `useSettings` consumer started from defaults, including RFID Off, before reading the owner cache in a microtask and then subscribing to saved preferences. Settings rendered the default immediately. The notification provider, dashboard bridge and Settings page maintained separate copies, listeners and cache writers.

Task 2 shares that existing preference state. It does not change RFID session ingestion, exit detection, replay, gas recovery, firmware, SQL, push delivery or polling intervals. The user authorized continuing locally while task 1's notification formatting awaits deployment acceptance.

## Change

- One root `SettingsProvider` serves all existing `useSettings` consumers and survives navigation. The existing notification document path, merge writes and owner-specific cache keys remain the same.
- State is keyed by owner UID, so account changes/logout discard prior settings immediately; refreshing the same owner does not reset preferences.
- Settings shows Checking until valid owner cache or a successful remote read establishes preferences. Missing/corrupt cache and a failed read do not claim that RFID is saved Off. A missing legacy offline snapshot is also not treated as a confirmed disabled preference.
- The settings listener requests metadata confirmations, and the existing operational adapter forwards that option to legacy Firestore. This allows a missing-document server confirmation after reconnect to resolve Checking without another request.
- Cleanup cancels queued hydration and ignores discarded snapshot callbacks. Unavailable browser storage does not prevent the remote subscription.
- The PWA install provider remains above the account-keyed state so authentication changes preserve the browser's one-shot install prompt.
- This replaces three independent settings listeners with one. Navigation adds no settings listener/read. This is a local lifecycle result, not a measured reduction in Vercel CPU usage.
